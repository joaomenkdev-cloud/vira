IDENTIDADE VISUAL — PLATAFORMA DE TICKETARIA
Você está trabalhando em uma plataforma de ticketaria/eventos já existente.
Sua responsabilidade nesta etapa é analisar o projeto atual e implementar uma identidade visual completa, consistente e profissional, sem destruir funcionalidades existentes.
A direção visual deve ser criada por você seguindo rigorosamente o briefing abaixo.
1. CONCEITO DA MARCA
A plataforma deve transmitir:

* eventos
* descoberta
* desejo
* facilidade
* confiança
* modernidade
* organização
* experiência premium

A sensação desejada é:
"Encontrar um evento e comprar o ingresso deve ser simples e prazeroso."
Não queremos que o produto pareça um sistema administrativo ou um SaaS corporativo.
O EVENTO é o protagonista.
2. DIREÇÃO VISUAL
Criar uma interface:

* clean
* premium
* contemporânea
* minimalista
* editorial
* bastante respirada
* visualmente forte sem ser exagerada

Priorizar:

* tipografia
* fotografia dos eventos
* hierarquia
* espaçamento
* contraste
* composição

Evitar elementos decorativos desnecessários.
A interface deve parecer desenhada por um bom designer de produto, e não montada a partir de componentes genéricos.
3. PALETA
Usar uma base predominantemente clara.
Base

* Branco / off-white para áreas principais
* Preto quase absoluto para títulos
* Cinzas neutros para textos secundários
* Cinzas muito claros para bordas e divisores

Cor de destaque
Utilizar uma única cor de ação forte:
Vermelho/coral vibrante.
Ela deve aparecer principalmente em:

* CTA principal
* preço/ações importantes quando fizer sentido
* estados ativos
* pequenos detalhes da marca
* elementos de interação

IMPORTANTE:
Não transformar a interface inteira em vermelho.
A cor deve funcionar como uma assinatura visual.
4. TIPOGRAFIA
Usar uma fonte moderna e extremamente legível.
Prioridade:

1. Inter
2. Geist
3. Manrope

Caso o projeto já tenha uma fonte adequada configurada, avaliar antes de substituir.
Hierarquia:
H1
Grande, pesado e com personalidade.
H2
Forte, mas menor.
Corpo
Regular, confortável e extremamente legível.
Labels
Pequenos, discretos e com bom contraste.
Não usar fontes decorativas.
5. PRINCÍPIO MAIS IMPORTANTE
O evento deve ser sempre o protagonista.
Em uma página de evento:
IMAGEM DO EVENTO
↓
NOME
↓
DATA / LOCAL
↓
DESCRIÇÃO
↓
INGRESSOS
↓
CTA
Não transformar a interface em uma coleção de componentes competindo entre si.
6. HOME
A home deve ter uma composição limpa.
Criar uma experiência de descoberta de eventos.
Possível estrutura:
Header
Logo à esquerda.
Navegação simples.
Possíveis itens:

* Explorar
* Eventos
* Meus ingressos

À direita:

* botão de login/perfil

O header deve ser extremamente limpo.
Evitar navbar gigantes.
HERO
Não criar aquele hero genérico de SaaS.
A primeira tela deve imediatamente comunicar:
"Encontre seu próximo evento."
Título grande.
Texto curto.
Busca/filtro de eventos de maneira elegante.
Pode existir uma imagem/evento em destaque, desde que a composição continue limpa.
EVENTOS EM DESTAQUE
Mostrar poucos eventos realmente relevantes.
Não criar uma parede de cards.
Cada card deve ter:

* imagem
* nome
* data
* localização
* preço inicial, quando disponível

A imagem deve ocupar boa parte do card.
Hover discreto.
Nada de sombras pesadas.
7. CARDS
Os cards precisam parecer premium.
Preferência:

* imagem grande
* borda muito sutil
* radius moderado
* informações bem espaçadas
* pouca decoração

Evitar:

* excesso de badges
* gradientes
* sombras enormes
* ícones desnecessários
* textos demais
* múltiplas cores

Um card bom deve ser compreendido em poucos segundos.
8. PÁGINA DO EVENTO
Esta é uma das páginas mais importantes.
Criar uma composição editorial.
Imagem/banner do evento em destaque.
Abaixo ou ao lado:
Nome do evento
Data
Horário
Local
Descrição.
Informações adicionais.
Área de compra.
O preço e a seleção do ingresso devem ter destaque suficiente, mas sem transformar a página em um formulário pesado.
CTA:
Comprar ingresso
deve ser extremamente evidente.
9. CHECKOUT
O checkout deve ser ainda mais clean.
Eliminar distrações.
Criar sensação de segurança.
Estrutura:

1. Evento
2. Tipo de ingresso
3. Quantidade
4. Dados do comprador
5. Pagamento
6. Resumo
7. Confirmar compra

O usuário precisa sempre saber:

* o que está comprando
* quanto está pagando
* em qual evento
* qual é o próximo passo

Não esconder informações importantes.
10. INGRESSO DIGITAL
Após a compra, o ingresso deve ter aparência premium.
Criar um componente visual semelhante a um ingresso moderno.
Informações:

* evento
* nome
* data
* horário
* local
* tipo de ingresso
* QR Code
* código/identificação

O QR Code deve ser visualmente destacado.
Pode utilizar detalhes discretos inspirados em tickets físicos:

* linha de corte
* pequenos recortes laterais
* divisórias
* microdetalhes

Mas sem exagerar.
11. MICROINTERAÇÕES
Adicionar somente quando agregarem qualidade.
Exemplos:

* hover suave em cards
* transições rápidas
* botão respondendo ao clique
* imagens com pequeno movimento
* feedback visual após compra
* loading states elegantes

Evitar animações chamativas.
A interface deve parecer rápida.
12. RESPONSIVIDADE
Mobile NÃO deve ser uma versão simplesmente reduzida do desktop.
Projetar pensando primeiro na experiência.
No mobile:

* header simplificado
* cards adaptados
* CTA de compra facilmente acessível
* informações importantes imediatamente visíveis
* checkout confortável para toque
* botões grandes o suficiente
* excelente espaçamento

13. ACESSIBILIDADE
Preservar e melhorar:

* contraste
* foco de teclado
* aria-labels
* navegação por teclado
* estados de erro
* estados de loading
* feedback de sucesso
* tamanho adequado dos elementos clicáveis

Não sacrificar acessibilidade pela estética.
14. DESIGN SYSTEM
Antes de sair estilizando página por página, identificar ou criar uma base consistente para:

* cores
* typography
* spacing
* radius
* shadows
* buttons
* inputs
* cards
* badges
* modals
* dropdowns
* loading
* alerts
* empty states

Não criar valores aleatórios diferentes em cada componente.
A interface inteira precisa parecer parte do mesmo produto.
15. O QUE NÃO FAZER
NÃO usar:

* roxo SaaS
* azul SaaS genérico
* gradientes exagerados
* glassmorphism
* neon
* excesso de sombras
* excesso de bordas
* cards dentro de cards dentro de cards
* dashboards visualmente carregados
* estética de template pronto
* excesso de ícones
* ilustrações genéricas
* texto inventado
* eventos fictícios para preencher a interface
* funcionalidades fictícias

Não invente informações de negócio.
Se alguma informação necessária não existir no projeto, preserve o comportamento atual ou sinalize a necessidade.
16. REGRAS PARA O CÓDIGO EXISTENTE
ANTES DE ALTERAR:

1. Inspecione a estrutura do projeto.
2. Identifique framework e sistema de estilos.
3. Identifique componentes reutilizáveis.
4. Identifique páginas existentes.
5. Identifique tokens/variáveis de design existentes.
6. Identifique componentes duplicados.
7. Entenda como os dados reais chegam à interface.

Não reescreva o projeto desnecessariamente.
Reutilize componentes existentes sempre que fizer sentido.
Não altere:

* regras de negócio
* APIs
* banco de dados
* autenticação
* pagamentos
* lógica de tickets
* integrações

a menos que uma alteração seja estritamente necessária para a implementação visual.
17. PROCESSO OBRIGATÓRIO
Trabalhe nesta ordem:
ETAPA 1 — AUDITORIA
Primeiro analise o projeto.
Não altere código ainda.
Identifique:

* stack
* estrutura
* páginas
* componentes
* estilos
* design system existente
* pontos inconsistentes
* problemas visuais
* componentes que podem ser reutilizados

Depois apresente um resumo objetivo.
ETAPA 2 — PLANO
Crie um plano de implementação dividido por responsabilidade.
Exemplo:

* foundation
* typography
* colors
* header
* home
* event page
* checkout
* ticket
* responsive
* states

Evite um único commit gigante.
ETAPA 3 — IMPLEMENTAÇÃO
Implemente progressivamente.
Prioridade:

1. foundation
2. componentes globais
3. header
4. home
5. página de evento
6. checkout
7. ingresso
8. responsividade
9. estados e refinamento

18. GIT
Seguir uma estratégia de pequenos commits.
Não criar um commit gigante.
Exemplo:

* feat(ui): establish visual foundation
* feat(ui): redesign header
* feat(ui): redesign event cards
* feat(ui): redesign home experience
* feat(ui): redesign event page
* feat(ui): redesign checkout
* feat(ui): redesign digital ticket
* fix(ui): refine responsive behavior
* fix(ui): polish accessibility states

Cada commit deve representar uma responsabilidade clara.
NÃO fazer squash/amend automaticamente.
NÃO fazer push ou deploy sem autorização explícita.
19. VALIDAÇÃO
Depois da implementação:

* executar build
* verificar erros
* verificar console
* verificar responsividade
* verificar overflow
* verificar imagens
* verificar estados vazios
* verificar loading
* verificar erros
* verificar acessibilidade
* verificar contraste
* verificar checkout
* verificar que nenhuma funcionalidade existente foi quebrada

Se houver Playwright ou ferramenta de browser disponível, utilizar para validar visualmente as páginas principais.
20. REGRA DE OURO
Não quero simplesmente uma "interface bonita".
Quero uma IDENTIDADE.
Quando alguém abrir diferentes páginas da plataforma, deve reconhecer imediatamente que tudo pertence à mesma marca.
A identidade precisa aparecer através de:

* tipografia
* espaçamento
* composição
* fotografia
* vermelho de destaque
* tratamento dos cards
* botões
* ingresso
* detalhes inspirados em ticket
* comportamento dos elementos

Tudo deve parecer intencional.
O resultado final deve transmitir:
clean + premium + eventos + confiança + desejo.
Menos elementos.
Mais impacto.
Mais espaço.
Mais hierarquia.
Mais personalidade.
